## はじめに

2026年9月9日、Rails Foundationが「Agents on Rails Stage 2」を公開しました。Fizzyというアプリに、20本の機能チケットを実装させるベンチマークです。

https://rubyonrails.org/2026/9/9/agents-on-rails-stage-2

Fizzyは、37signalsがRailsで作ったカンバン型のツールです。課題やアイデアをカードで管理でき、ソースも公開されています。

Stage 1では、半分以上の解答がフレームワークを使わずに車輪を再発明していました。そこでStage 2では、タスクを機能単位に大きくしています。合格率の最高はGPT-6 Astraの35%でした。Fable 5.1は32%(1回$9.14)、Opus 5は25%(同$9.85)です。

9月23日のRails World基調講演では、DHHが次の3つを話しました。

https://www.youtube.com/watch?v=vDjW_dRyKXY

- 37signalsは手でコードを書くのをやめた。エージェントが失敗したら、工場の側を直す
- 設定より規約は、トークン効率につながる
- アプリには、利用者のエージェントが使えるCLIを付けるべき

Gurenは、筆者が開発しているBun向けのフルスタックフレームワークです。Gurenとハーネス(エージェント向けの設定一式)、計測の方法は、8月に実施した第1弾で紹介しました。

https://zenn.dev/7nohe/articles/agents-on-guren-benchmark

本記事では、第1弾から変えた点と、次の2つの結果を紹介します。

- Part A(21セル): 同じブログアプリにタグ機能を足すコストを、GurenとHonoで比べた
- Part B(225セル): Gurenのブログに9本のチケットを実装させた比較。4モデルで、ハーネスあり・なしを比べた

## 1. Part A: GurenとHonoの実装コスト比較

### 計測方法

framework-comparisonリポジトリでは、同じ仕様の小さなブログを、複数のフレームワークで実装しています。ログイン、投稿、コメント、検証、通知、テストまでそろったアプリです。

https://github.com/gurenjs/framework-comparison

Part Aでは、このアプリにタグ機能を足すタスクを、GurenとHonoの実装に解かせました。DBのテーブル追加とマイグレーション、Reactのフォームと表示、`?tag=`の絞り込み、検証、テストまで含みます。typecheck、アプリのテスト、隠しHTTPスモークがすべて通れば合格です。

Honoの実装は、Hono、Drizzle、ReactのSPAを手で組み合わせた構成です。GurenもHono、Drizzle、Reactの上に作ったフレームワークなので、この比較ではGurenの規約がエージェントのコストをどれだけ増やすかを見ています。

なお、このタスクは完成したアプリに機能を足すもので、アプリの土台を作るコストは含みません。同じリポジトリの計測では、アプリ全体を作るのに手で書いたコードは、Gurenが632行、Honoが977行でした。

7月の計測では、GurenはHonoの1.65倍のコストでした。今回は次の条件で測り直しました。

- ランナーを隔離した。実行者個人の設定、MCPサーバー、auto memoryは読み込まない
- Gurenのアプリは計測時点の最新版にし、ハーネスも作り直した
- 対照として、Honoと7月時点のGurenアプリ(cli 2.0)も流した。7月からのコストの変化が、Gurenのリリースによるものかを見るためです
- 21セルすべてが合格した

### 結果

| arm | モデル | ターン(範囲) | コスト(範囲) | Hono比 |
|---|---|---|---|---|
| Hono | Sonnet 5.5 | 40(29〜42) | $0.41($0.38〜0.46) | 1.00倍 |
| Guren、shippedハーネス(cli 2.27) | Sonnet 5.5 | 38(30〜41) | $0.57($0.56〜0.61) | 1.40倍 |
| Guren、ハーネスなし | Sonnet 5.5 | 51(47〜52) | $0.63($0.58〜0.69) | 1.54倍 |
| Guren、7月時点のアプリ(cli 2.0) | Sonnet 5.5 | 33(32〜37) | $0.57($0.49〜0.64) | 1.38倍 |
| Guren、shippedハーネス(cli 2.28) | Sonnet 5.5 | 38(37〜43) | $0.52($0.50〜0.63) | 1.26倍 |
| Hono | Opus 5.5 | 40(38〜41) | $0.88($0.83〜0.91) | 1.00倍 |
| Guren、shippedハーネス(cli 2.27) | Opus 5.5 | 40(38〜45) | $1.32($1.31〜1.55) | 1.49倍 |

数値は3回の中央値で、括弧内は最小と最大です。コストはCLIが表示するAPI換算の金額です。

- 「cli 2.28」は、cli 2.27の次のリリースのハーネスです。ruleの読み込み方の修正などが入っています。Hono比は中央値で1.26倍、平均で1.32倍でした
- Sonnetの行は、最初はSonnet 5で測りました。Sonnet 5.5が出たので流し直しましたが、比率はあまり変わっていません(shippedは1.44倍から1.40倍)

表から読めることは次のとおりです。

- GurenはHonoよりコストが高いものの、ターン数はほぼ同じです(Sonnetで38対40)。差は、1ターンごとに読み込む文脈の量にあります
- ハーネスを入れると、ターン数は25%、コストは8〜9%減りました。ただし、3回の範囲は重なっています
- 現行のアプリは、7月時点のアプリより安くなっていません。そのため、時間とともに改善したとは主張しません
- Sonnetでは、7月に$2〜3台だったコストが、今回はすべて1ドル未満になりました。7月時点のアプリも同じように下がったので、原因はGurenのリリースではありません。ランナーの隔離が原因だと考えていますが、確かめてはいません

### コスト差の内訳

Sonnet 5.5のログから、エージェントの操作を次の3種類に分けました。そのうえで、それぞれが使ったトークンを集計しています。直接測った値ではなく、分類のルールに基づく推定です。

- 名前の迷い: 関数が`@guren/core`と`@guren/server`のどちらにあるかを探す操作。2つのパッケージを統合すれば消せます
- APIの学習: `node_modules`やガイダンスを読む操作と、セッション開始時に読み込むガイダンス
- 実装: アプリのファイルの読み書き、codegen、テストなど
- その他: 途中で読み込まれるruleの本文、エージェントの文章など

次の表は、1回あたりの平均で、HonoよりGurenが多くかかった金額を作業の種類ごとに分けたものです。マイナスは、Honoより少なかったことを表します。

| arm | Honoとの差 | 名前の迷い | APIの学習 | 実装 | その他 |
|---|---|---|---|---|---|
| Guren shipped | $0.167 | $0.000 | $0.179 | −$0.012 | $0.001 |
| Guren bare | $0.220 | $0.012 | $0.097 | $0.093 | $0.017 |
| Guren shipped(cli 2.28) | $0.135 | $0.000 | $0.074 | $0.028 | $0.033 |

- shippedでは、Honoとの差のすべてが、最初に読み込むガイダンスの分でした。ガイダンスは25.5kトークンあり、呼び出しのたびに読み直すので、1回あたり$0.17〜0.19かかります。実装のコストは、Honoよりわずかに少なくなっています
- ハーネスなしでは、3回中2回で`paginate()`の場所を探していました。ハーネスありでは、この探索はありませんでした
- cli 2.28では、最初に読み込むガイダンスが7.1kトークンに減りました。Honoとの差も最も小さくなっています

## 2. Part B: 9本のプロダクトチケットでのハーネス比較

### タスク

第1弾の小さなタスクでは、SonnetとOpusがほぼ全問に合格し、差がつきませんでした。そこで今回は、Railsと同じくタスクを大きくしました。

チケットは、プロダクトオーナーが書く依頼文の形にしています。何を、なぜ作るのかだけを書き、使うAPIは書いていません。対象は`create-guren-app`で作ったばかりのブログで、どのチケットも複数の機能にまたがります。

| チケット | 内容 | 隠しテスト |
|---|---|---|
| post-tags | 投稿へのタグ、`?tag=`絞り込み、1投稿5個まで(Part Aと同じ仕様をこのアプリで) | 6 |
| comments-moderation | コメント、作者か記事の作者だけが削除できる、3人の通報で非表示 | 8 |
| post-revisions | 編集ごとの履歴、一覧と復元、作者のみ | 6 |
| scheduled-publish | 公開予約、それまで他人には見えない、予約一覧を出すconsoleコマンド | 7 |
| json-api-tokens | 個人APIトークン、bearer認証のJSON API、トークンごと毎分60リクエスト | 10 |
| locale-switch | 日本語対応、言語切替の保持、`guren check --i18n`が通るカタログ | 13 |
| newsletter-module | ニュースレター登録をアプリケーションモジュールとして実装し、アーキテクチャ規則でブログ側からの依存を禁止 | 14 |
| posts-agent-tool | 記事の検索と作成をMCP経由のエージェントツールとして公開、read-onlyの宣言が正しい | 11 |
| cover-attachment | 表紙画像(PNGかJPEG、2MBまで)、差し替え、削除、記事と一緒に消える | 9 |

- 合格の条件は第1弾と同じです。隠しテストは9本で合計84本あります
- 今回は、権限のない削除ができてしまったら不合格にしました
- 課題文には、テーブル名やルート、ステータスコードを書いています。隠しテストを安定させるためです
- 9本 × 4モデル × ハーネスあり・なし × 3回で216セルです。これに、計画を渡す条件の9セルを足して225セルになります
- API換算のコストは$477.84でした

### 結果

| モデル | 合格(bare) | 合格(shipped) | ターン中央値 | コスト中央値 | コスト差(中央値) | コスト差(平均) |
|---|---|---|---|---|---|---|
| Sonnet 5.5 | 26/27(96%) | 27/27 | 37 → 29(−22%) | $0.57 → $0.61 | +7% | +1% |
| Opus 5.5 | 27/27 | 27/27 | 59 → 43(−27%) | $1.51 → $1.29 | −14% | −11% |
| Haiku 4.5 | 8/27(30%) | 12/27(44%) | 90 → 80(−11%) | $0.79 → $0.89 | +13% | +10% |
| Fable 5.1 | 27/27 | 27/27 | 99 → 78(−21%) | $6.27 → $5.42 | −13% | −16% |

- ハーネスを入れると、どのモデルもターン数が減りました
- OpusとFableは、コストも下がりました
- Sonnetは、コストがわずかに増えました。セッションが短いぶん、最初に読み込むガイダンスの割合が大きいのかもしれません
- Haikuは、ターン数が減ったのにコストが増えました。1ターンあたりのコストが上がっています
- 合格率は、Haiku(30%から44%)とSonnetの1回分しか変わりませんでした

| チケット | Sonnet bare | Sonnet shipped | Opus 5.5 bare / shipped | Haiku bare | Haiku shipped | Fable bare / shipped |
|---|---|---|---|---|---|---|
| post-tags | 3/3 | 3/3 | 3/3 · 3/3 | 0/3 | 2/3 | 3/3 · 3/3 |
| comments-moderation | 3/3 | 3/3 | 3/3 · 3/3 | 1/3 | 3/3 | 3/3 · 3/3 |
| post-revisions | 3/3 | 3/3 | 3/3 · 3/3 | 3/3 | 3/3 | 3/3 · 3/3 |
| scheduled-publish | 3/3 | 3/3 | 3/3 · 3/3 | 2/3 | 1/3 | 3/3 · 3/3 |
| json-api-tokens | 3/3 | 3/3 | 3/3 · 3/3 | 2/3 | 3/3 | 3/3 · 3/3 |
| locale-switch | 3/3 | 3/3 | 3/3 · 3/3 | 0/3 | 0/3 | 3/3 · 3/3 |
| newsletter-module | 2/3 | 3/3 | 3/3 · 3/3 | 0/3 | 0/3 | 3/3 · 3/3 |
| posts-agent-tool | 3/3 | 3/3 | 3/3 · 3/3 | 0/3 | 0/3 | 3/3 · 3/3 |
| cover-attachment | 3/3 | 3/3 | 3/3 · 3/3 | 0/3 | 0/3 | 3/3 · 3/3 |

- Sonnetが落とした1回は、mass assignmentの問題でした。`fillable`にない`confirmedAt`を`update()`で書こうとして、確認リンクが500を返しました
  - エージェント自身のテストは通っていて、採点用の隠しテストで失敗しました
  - ハーネスには`fillable`の説明がありますが、1回の失敗だけでは効果があったとは言えません
- Haikuは、4本のチケットを全回で落としました
- posts-agent-toolは、DHHの「アプリにCLIを」に最も近いチケットです。ルートをMCPのツールとして公開します。Sonnet、Opus、Fableは全回合格、Haikuは全回不合格でした
- RailsのStage 1と同じく、上位モデルは合格率が頭打ちです。ハーネスの効果は、合否ではなくターン数とコストに出ています
- Railsの35%とは比べられません。ランナーもアプリの規模も違い、こちらはチケットの仕様を細かく決めています

### フレームワークの機能を使ったか

合格した回について、チケットに対応するフレームワークの機能(添付ファイル、レート制限など)を使ったか、使わずに同じ処理を自前で書いたかを調べました。Railsの記事では、後者を「車輪の再発明」と呼んでいます。

| モデル | 条件 | 合格 | 機能を使用 | 両方 | 自前で実装 |
|---|---|---|---|---|---|
| Sonnet 5.5 | bare | 26 | 13 | 10 | 3 |
| Sonnet 5.5 | shipped | 27 | 15 | 9 | 3 |
| Opus 5.5 | bare | 27 | 22 | 5 | 0 |
| Opus 5.5 | shipped | 27 | 20 | 7 | 0 |
| Haiku 4.5 | bare | 8 | 4 | 4 | 0 |
| Haiku 4.5 | shipped | 12 | 4 | 8 | 0 |
| Fable 5.1 | bare | 27 | 19 | 8 | 0 |
| Fable 5.1 | shipped | 27 | 21 | 6 | 0 |

- 自前で実装したのは6件だけで、すべてSonnetのcover-attachmentです。フレームワークの添付機能を使わず、ファイルを自前で書き込んでいました
- ハーネスの有無で、この集計はほとんど変わりませんでした
- 判定は正規表現による大まかなものです。自前で書いたらしいコードが1か所でもあると「両方」になります。そのため、チケットが求める204応答のように、手で書くのが正しいコードも含まれています

## 3. 承認済みの実装計画の使われ方

Gurenには、実装計画の仕組みがあります。人間が計画を承認し、エージェントが1ステップずつ実装します。ステップごとに`plan:next`で次の作業を受け取り、`plan:verify`で検証する流れです。DHHの言う「工場」にあたります。

3本のチケットに承認済みの計画を付け、「計画を実装せよ」と指示しました。モデルはSonnet 5.5で、3回ずつ流しています。

| セル | `plan:next` 呼び出し | `plan:verify` 呼び出し | コミット | ターン |
|---|---|---|---|---|
| post-tags 1 / 2 / 3 | 1 / 1 / 3 | 0 / 0 / 1 | 0 / 0 / 0 | 39 / 57 / 40 |
| comments-moderation 1 / 2 / 3 | 1 / 0 / 1 | 0 / 0 / 0 | 0 / 0 / 0 | 28 / 31 / 42 |
| scheduled-publish 1 / 2 / 3 | 0 / 1 / 0 | 0 / 1 / 0 | 0 / 0 / 0 | 37 / 27 / 28 |

- 計画の有無にかかわらず、9回すべて合格しました。計画付きの方が、ターン数もコストも多くかかりました
- 「1ステップ、1検証、1コミット」で進めた回はありませんでした。どの回も、計画を読んで一度に実装しています
- 作業の終わりに動くStopフックは、`plan:next`で受け取ったステップしか確認しません。そのため、一度に実装しても止められませんでした。未検証のステップが残る間は止める必要があります

## 4. 注意点

- ランナーは、headlessのClaude Codeだけです
- 試行は各3回です。傾向は見えますが、効果があると言い切れる数ではありません
- チケットは自作で、仕様を細かく決めています。そのぶん、実際の開発のチケットより易しくなっています
- Part AとPart Bは、ランナーの細かい設定が違います。コストの金額は比べられません
- 今回は、セッション開始時、編集後、終了時の3つのフックがすべて動きました。終了時のフックは、Sonnetで3回、Haikuで1回、エージェントの終了を止めました
- Opus 5.5は、第1弾やRailsで使われたOpus 5とは別の世代です
- このチケットでは上位モデルが全問合格するので、差を見るにはもっと難しいチケットが要ります

## まとめ

- 上位モデル(Opus 5.5、Fable 5.1、ハーネスありのSonnet 5.5)は、9本の機能チケットにすべて合格しました。認可、APIトークン、多言語化、モジュール、MCPツール、添付ファイルにまたがるチケットです
- 合格した実装のほとんどは、Gurenに最初からある機能を使っていました。機能を使わずに自前で書いたのは6件だけです
- ハーネスを入れると、OpusとFableのターン数は21〜27%減りました
- アプリのルートをMCPツールとしてエージェントに公開するチケットも、上位3モデルが全回で通しました
- 完成したアプリに機能を1つ足すコストは、最新のハーネスでHonoの構成の1.26倍で、ターン数は同じでした。差は、最初に読み込むガイダンスの分です。一方、アプリの土台を作るのに手で書くコードは、GurenのほうがHonoより3分の1ほど少なく済みます
- 承認済みの計画を渡しても、1ステップずつ進めたエージェントはいませんでした。ここは今後の課題です
- 計測の途中でGuren自身の問題が22件見つかり、10件は修正済みです

## おわりに

Gurenでは、エージェント向けの設定一式を入れた状態でアプリを作れます。

```bash
bunx create-guren-app my-app --agents claude
```

ドキュメントや、エージェントと一緒にアプリを作るコースはguren.devにあります。

https://guren.dev
