## はじめに

2026年9月23日のRails World基調講演で、DHHは「設定より規約は、トークン効率につながる」と話しました。

https://www.youtube.com/watch?v=vDjW_dRyKXY

ただ、Railsの規約は、モデルが学習データで何度も見ているものです。モデルがよく知らない規約でも、同じことが言えるのでしょうか。

Gurenは、筆者が開発しているBun向けのフルスタックフレームワークです。Hono、Drizzle、Reactの上に、Laravel風の規約を載せています。まだ新しいので、モデルはこの規約をほとんど知りません。そこで、規約はガイダンス(CLAUDE.md、ルール、スキルなど、エージェント向けの説明一式)で教えています。第1弾では、ガイダンスの有無でエージェントの手数が変わることを紹介しました。

https://zenn.dev/7nohe/articles/agents-on-guren-benchmark

本記事では、次の2つを測った結果から、この問いに答えます。

- 知らない規約を教えると、どれだけコストがかかるか
- 教えた規約を、エージェントは実際に使うか

## 1. 知らない規約を教えるコスト

### 計測方法

GurenはHonoの上に作ったフレームワークです。そこで、規約のないHonoの構成と比べれば、規約を教えるコストだけを取り出せると考えました。

framework-comparisonリポジトリには、同じ仕様の小さなブログが、複数のフレームワークで実装されています。ログイン、投稿、コメント、検証、テストまでそろったアプリです。

https://github.com/gurenjs/framework-comparison

このアプリにタグ機能を足すタスクを、GurenとHonoの実装に解かせました。DBのテーブル追加とマイグレーション、Reactのフォームと表示、`?tag=`の絞り込み、検証、テストまで含みます。typecheck、アプリのテスト、隠しHTTPスモークがすべて通れば合格です。

Honoの実装は、Hono、Drizzle、ReactのSPAを手で組み合わせた構成です。土台の部品はGurenと同じなので、違いはGurenの規約だけになります。

### 規約とガイダンスの例

たとえば、Gurenアプリの投稿一覧は次のように書きます。コントローラーは`app/Http/Controllers`に置き、クエリは`validateQuery()`で検証します。一覧はモデルの`paginate()`で取り出し、`@guren/core`の`paginate()`でページ送りのリンクを付けて、Inertiaのページに渡します。

```ts:app/Http/Controllers/PostController.ts
export default class PostController extends Controller {
  async index() {
    const { page } = this.validateQuery(ListPostsQuerySchema)
    const result = await Post.paginate({ page, perPage: 10, orderBy: ['createdAt', 'desc'] })
    const paginator = paginate(result, { path: this.request.path ?? '/posts' })

    return this.inertia(pages.posts.Index, {
      data: result.data.map((post) => new PostResource(post).toJSON()),
      pagination: { meta: paginator.meta(), links: paginator.links() },
    })
  }
}
```

この書き方は、ガイダンスのルールファイルで教えています。たとえばページ送りについては、次のように書いてあります。

```md:.claude/rules/orm-models.md(抜粋)
For Inertia/HTTP pagination links wrap it with `paginate` from `@guren/core`:
`paginate(result, { path?, query?, fragment? })` — those three fields are `PaginatorOptions`.
```

ガイダンスがないと、エージェントはこうした書き方を型定義から探すことになります。実際、ガイダンスなしの3回中2回は、この`paginate()`の使い方を探して型定義を読み回っていました。

### 結果

| 構成 | モデル | ターン | コスト | Hono比 |
|---|---|---|---|---|
| Hono | Sonnet 5.5 | 40 | $0.41 | 1.00倍 |
| Guren、ガイダンスなし | Sonnet 5.5 | 51 | $0.63 | 1.54倍 |
| Guren、ガイダンスあり(25.5kトークン) | Sonnet 5.5 | 38 | $0.57 | 1.40倍 |
| Guren、ガイダンスを絞った版(7.1kトークン) | Sonnet 5.5 | 38 | $0.52 | 1.26倍 |
| Hono | Opus 5.5 | 40 | $0.88 | 1.00倍 |
| Guren、ガイダンスあり(25.5kトークン) | Opus 5.5 | 40 | $1.32 | 1.49倍 |

各3回の中央値です。コストはCLIが表示するAPI換算の金額です。

- ガイダンスがないと、Gurenは最もターン数が多くなりました。関数がどのパッケージにあるかを探す操作も出ています
- ガイダンスを入れると、ターン数はHonoと同じになりました。規約を教えれば、迷わずに書けています
- それでも、コストはHonoの1.26〜1.49倍です

### 差はどこから来ているか

Sonnet 5.5のログから操作を分類し、Honoとの差がどの作業から来ているかを集計しました。直接測った値ではなく、分類のルールに基づく推定です。

| 構成 | Honoとの差 | ガイダンスを読む | 実装 | その他 |
|---|---|---|---|---|
| Guren、ガイダンスなし | $0.220 | $0.109 | $0.093 | $0.017 |
| Guren、ガイダンスあり(25.5k) | $0.167 | $0.179 | −$0.012 | $0.001 |
| Guren、ガイダンスを絞った版(7.1k) | $0.135 | $0.074 | $0.028 | $0.033 |

「ガイダンスを読む」には、ガイダンスのほか、`node_modules`の型定義を読む操作も含みます。マイナスは、Honoより少なかったことを表します。

- ガイダンスありでは、差のすべてがガイダンスを読む分でした。実装そのものは、Honoよりわずかに安く済んでいます
- ガイダンスは、エージェントがモデルを呼び出すたびに読み直されます。25.5kトークンのガイダンスで、1回あたり$0.17〜0.19かかりました
- ガイダンスを7.1kトークンに絞ると、差は$0.135まで縮みました

なお、この比較は、完成したアプリに機能を1つ足すコストです。アプリの土台を作るのに手で書いたコードは、Gurenが759行、Honoが977行でした(生成コマンドが出力したコードを除いた行数)。

## 2. 教えた規約は使われるか

### タスク

Gurenで作ったブログに、9本の機能チケットを実装させました。チケットは、プロダクトオーナーが書く依頼文の形にしています。何を作るかだけを書き、使うAPIは書いていません。

| チケット | 内容 |
|---|---|
| post-tags | 投稿へのタグ、`?tag=`絞り込み、1投稿5個まで |
| comments-moderation | コメント、作者か記事の作者だけが削除できる、3人の通報で非表示 |
| post-revisions | 編集ごとの履歴、一覧と復元、作者のみ |
| scheduled-publish | 公開予約、それまで他人には見えない、予約一覧を出すコマンド |
| json-api-tokens | 個人APIトークン、bearer認証のJSON API、トークンごと毎分60リクエスト |
| locale-switch | 日本語対応、言語切替の保持 |
| newsletter-module | ニュースレター登録を独立したモジュールとして実装 |
| posts-agent-tool | 記事の検索と作成を、MCP経由のエージェントツールとして公開 |
| cover-attachment | 表紙画像(PNGかJPEG、2MBまで)、差し替え、削除 |

4つのモデルで、ガイダンスあり・なしを各3回流しました。合格の条件は、採点用の隠しテスト(合計84本)とtypecheckがすべて通ることです。

### 結果

| モデル | 合格(なし → あり) | ターン | コスト |
|---|---|---|---|
| Sonnet 5.5 | 26/27 → 27/27 | 37 → 29(−22%) | $0.57 → $0.61 |
| Opus 5.5 | 27/27 → 27/27 | 59 → 43(−27%) | $1.51 → $1.29 |
| Haiku 4.5 | 8/27 → 12/27 | 90 → 80(−11%) | $0.79 → $0.89 |
| Fable 5.1 | 27/27 → 27/27 | 99 → 78(−21%) | $6.27 → $5.42 |

ターンとコストは中央値です。

- Opus、Fable、ガイダンスありのSonnetは、9本すべてに合格しました。モデルがよく知らないフレームワークでも、機能単位の実装はこなせています
- ガイダンスを入れると、どのモデルもターン数が11〜27%減りました
- コストが下がったのは、セッションの長いOpusとFableです。Sonnetはほぼ変わらず、Haikuは増えました
- 合格率が上がったのは、Haikuだけです(30%から44%)

### フレームワークの機能を使ったか

合格した181回のうち、チケットに対応するGurenの機能(添付ファイル、レート制限など)を使わずに、同じ処理を自前で書いたのは6回だけでした。残りの175回は、Gurenの機能を使っています。

- これはガイダンスなしでも同じでした。ガイダンスがなくても、エージェントは自分で機能を見つけて使っています
- 1の内訳を見る限り、ガイダンスが減らしているのは機能を探す手間だと考えられます。その分、ターン数が減っています

## 3. CLAUDE.mdを書くときの示唆

Gurenに限らず、自分のプロジェクトの規約をエージェントに教えるときにも、同じことが言えそうです。

- ガイダンスは、呼び出しのたびに読み直される固定費です。量がそのままコストになるので、常に読み込む内容は絞ったほうがよいです
- ガイダンスの効果は、ターン数に出ます。今回は、セッションが長いモデルほどコストも下がりました。長い作業ほど、固定費を取り返しやすいようです
- 上位モデルでは、ガイダンスの有無で合否は変わりませんでした。差が出るのは、手数とコストです
- フレームワークの機能は、ガイダンスがなくても見つけて使われました。ガイダンスに書くべきなのは、探す手間を省く情報です

## 4. 注意点

- ランナーは、headlessのClaude Codeだけです
- 試行は各3回です。傾向は見えますが、効果があると言い切れる数ではありません
- チケットは自作で、仕様を細かく決めています。そのぶん、実際の開発のチケットより易しくなっています
- 1と2は、ランナーの細かい設定が違います。コストの金額は比べられません
- Railsでの計測ではないので、Railsの規約がどれだけ効くかは分かりません

## まとめ

- 今回の結果から言えるのは、規約がトークン効率につながるのは、モデルがその規約を知っている場合だということです
- 知らない規約は、ガイダンスで教えればエージェントに使われます。上位モデルは9本の機能チケットにすべて合格し、実装のほとんどはフレームワークの機能を使っていました
- ただし、教えるためのガイダンスは、呼び出しのたびにコストになります。機能を1つ足すコストは、Honoの1.26〜1.49倍でした
- ガイダンスを絞るほど、その差は小さくなります

## おわりに

Gurenには、認証や認可、添付ファイル、レート制限、MCPツールの公開など、アプリに必要な機能が最初からそろっています。今回の計測でも、エージェントはこれらの機能を使って9本のチケットを実装しました。アプリの土台を作るのに手で書くコードも、HonoとReactを手で組むより2割ほど少なく済みます。

エージェント向けのガイダンス(CLAUDE.md、ルール、スキル、hooks)を入れた状態で、すぐにアプリを作れます。ぜひ試してみてください。

```bash
bunx create-guren-app my-app --agents claude
```

ドキュメントや、エージェントと一緒にアプリを作るコースはGuren公式サイトにあります。

https://guren.dev
